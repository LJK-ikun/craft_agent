#### 1. MCP 协议适配层设计

**文件位置：** `packages/shared/src/mcp/mcp-pool.ts`

**核心架构：**

**设计亮点：**

1. **集中式连接池管理**
   - 所有 MCP 连接统一管理，避免重复连接
   - 支持 3 种传输协议：HTTP、SSE、stdio
   - 跨 Session 共享连接（如多个会话共用同一个 Linear 连接）

2. **工具名称代理机制**
   ```typescript

   // 代理名称：mcp__linear__createIssue
   proxyToolName(slug, toolName) {
     return `mcp__${slug}__${toolName}`;
   }
   ```
   - 避免不同 MCP Server 的工具名冲突
   - 统一命名规范，便于路由和调试

3. **动态同步与热重载**
   ```typescript
   async sync(mcpServers, apiServers) {
     // 1. 断开已删除的源
     for (const slug of currentSlugs) {
       if (!desiredSlugs.has(slug)) await this.disconnect(slug);
     }
     
     // 2. 连接新增的源
     for (const [slug, config] of Object.entries(filteredMcp)) {
       if (!currentSlugs.has(slug)) await this.connect(slug, config);
     }
     
     // 3. 重连配置变更的源（如 OAuth Token 刷新）
     if (mcpConfigChanged(oldConfig, newConfig)) {
       await this.disconnect(slug);
       await this.connect(slug, newConfig);
     }
   }
   ```

#### 3. AES-256-GCM 加密存储

**文件位置：** `packages/shared/src/credentials/backends/secure-storage.ts`

**加密方案设计：**

1. **文件格式**
   ```
   [Header - 64 bytes]
   ├── Magic: "CRAFT01\0" (8 bytes)
   ├── Flags: uint32 LE (4 bytes)
   ├── Salt: 32 bytes (PBKDF2 salt)
   └── Reserved: 20 bytes
   
   [Encrypted Payload]
   ├── IV: 12 bytes (随机生成)
   ├── Auth Tag: 16 bytes (GCM 认证标签)
   └── Ciphertext: variable (加密的 JSON)
   ```

2. **密钥派生（PBKDF2）**
   ```typescript
   function getEncryptionKey(salt: Buffer): Buffer {
     // 1. 获取硬件 UUID（跨平台）
     const stableMachineId = getStableMachineId();
     
     // 2. SHA-256 哈希
     const hash = createHash('sha256')
       .update(stableMachineId)
       .update('craft-agent-v2')
       .digest();
     
     // 3. PBKDF2 密钥派生（100,000 次迭代）
     return pbkdf2Sync(hash, salt, 100000, 32, 'sha256');
   }
   ```

3. **跨平台硬件 UUID 获取**
   ```typescript
   function getStableMachineId(): string {
     if (process.platform === 'darwin') {
       // macOS: IOPlatformUUID（主板唯一 ID）
       return execSync('ioreg -rd1 -c IOPlatformExpertDevice | grep IOPlatformUUID');
     } 
     else if (process.platform === 'win32') {
       // Windows: MachineGuid（注册表）
       return execSync('reg query HKLM\\SOFTWARE\\Microsoft\\Cryptography /v MachineGuid');
     } 
     else {
       // Linux: /var/lib/dbus/machine-id
       return readFileSync('/var/lib/dbus/machine-id', 'utf-8').trim();
     }
   }
   ```

4. **AES-256-GCM 加密/解密**
   ```typescript
   // 加密
   const iv = randomBytes(12);  // 每次写入生成新 IV
   const cipher = createCipheriv('aes-256-gcm', key, iv);
   const ciphertext = Buffer.concat([
     cipher.update(plaintext),
     cipher.final()
   ]);
   const authTag = cipher.getAuthTag();  // 16 字节认证标签
   
   // 解密
   const decipher = createDecipheriv('aes-256-gcm', key, iv);
   decipher.setAuthTag(authTag);
   const decrypted = Buffer.concat([
     decipher.update(ciphertext),
     decipher.final()
   ]);
   ```

5. **自动迁移机制**
   ```typescript
   // 尝试新版密钥解密
   let store = tryDecrypt(encryptedData, newKey);
   
   if (!store) {
     // 尝试旧版密钥（基于 hostname）
     store = tryDecrypt(encryptedData, legacyKey);
     
     if (store) {
       // 迁移：用新密钥重新保存
       this.saveStoreSync(store);
     }
   }
   ```

### 技术难点与解决方案

#### 难点 1：跨平台硬件 UUID 获取

**问题：** 不同操作系统的硬件标识方式不同

**解决方案：**
- macOS: `ioreg` 命令读取 IOPlatformUUID
- Windows: 注册表查询 MachineGuid
- Linux: 读取 `/var/lib/dbus/machine-id`
- Fallback: `username:homedir`

#### 难点 2：OAuth Token 刷新时机

**问题：** Token 过期后用户体验中断

**解决方案：**
- 存储 `expiresAt` 时间戳
- 每次请求前检查：`if (Date.now() + 5*60*1000 > expiresAt)`
- 自动调用 `refreshToken()` 更新凭证

#### 难点 3：MCP 工具名冲突

**问题：** 不同 MCP Server 可能有同名工具

**解决方案：**
- 代理命名：`mcp__${slug}__${toolName}`
- 冲突检测：相同代理名保留第一个，跳过后续
- 日志警告：`console.warn('Proxy name collision')`

#### 难点 4：加密文件的兼容性迁移

**问题：** 旧版本用 hostname 派生密钥，hostname 变化后无法解密

**解决方案：**
- 新版本用硬件 UUID 派生密钥
- 读取时先尝试新密钥，失败后尝试旧密钥
- 用旧密钥成功后，立即用新密钥重新保存

### 可展开的面试话术

**问：你们是怎么实现零配置集成的？**

答：我们设计了一个 MCP 协议适配层 + OAuth 认证系统。核心是三层架构：

1. **MCP Client Pool**: 集中管理所有外部服务连接，支持 HTTP/SSE/stdio 三种传输协议，跨 Session 复用连接。

2. **OAuth Flow Manager**: 实现了 PKCE 授权码流程，支持 Google、Slack、Microsoft 等 12 个平台。用户只需点击授权，系统自动完成 Token 获取、存储、刷新。

3. **Credential Storage**: 使用 AES-256-GCM 加密存储 Token，密钥通过 PBKDF2 从硬件 UUID 派生，100,000 次迭代保证安全性。

用户体验上，只需对话 "帮我连接 Google Calendar"，Agent 自动打开浏览器授权，完成后即可调用工具，完全零配置。

**问：为什么选择 AES-256-GCM 而不是系统 Keychain？**

答：主要是跨平台兼容性和用户体验考虑：

1. **跨平台一致性**: macOS Keychain、Windows Credential Manager、Linux libsecret 的 API 差异很大，统一的文件加密方案更易维护。

2. **无权限弹窗**: 系统 Keychain 每次读取都会弹窗，影响自动化流程。文件加密只需一次解密，性能更好。

3. **可移植性**: 加密文件可以通过云盘同步到多台设备（密钥绑定硬件，其他设备无法解密，保证安全）。

4. **安全性**: AES-256-GCM 是 NIST 推荐的 AEAD 算法，提供机密性和完整性保护。PBKDF2 100,000 次迭代足以抵抗暴力破解。

#### 2. 三级权限系统

**文件位置：** `packages/shared/src/agent/core/permission-manager.ts`

**三个权限等级：**

| 模式 | 名称 | 行为 | 使用场景 |
|------|------|------|----------|
| `safe` | 只读模式 | 所有写操作被拦截 | 探索代码库，不做修改 |
| `ask` | 询问模式 | 写操作需要人工确认 | 日常开发（默认） |
| `allow-all` | 自动模式 | 所有操作自动执行 | 自动化任务 |

**核心实现：**

1. **权限检查流程**
   ```typescript
   class PermissionManager {
     evaluateToolCall(toolName: string, toolInput: Record<string, unknown>) {
       const mode = this.getPermissionMode();
       
       // 1. 检查工具类型
       if (isReadOnlyTool(toolName)) {
         return { allowed: true };  // 只读工具总是允许
       }
       
       // 2. 检查权限模式
       if (mode === 'safe') {
         return { 
           allowed: false, 
           reason: '只读模式下禁止写操作' 
         };
       }
       
       if (mode === 'allow-all') {
         return { allowed: true };  // 自动模式总是允许
       }
       
       // 3. 询问模式：需要人工确认
       if (mode === 'ask') {
         return {
           allowed: true,
           requiresPermission: true,  // 标记需要确认
           description: formatToolDescription(toolName, toolInput)
         };
       }
     }
   }
   ```

2. **危险命令黑名单**

### 可展开的面试话术

**问：WebSocket RPC 协议相比传统 HTTP 有什么优势？**

答：主要有三点：

1. **双向通信**：HTTP 是单向的（请求-响应），而 WebSocket 支持服务器主动推送。我们的场景需要实时推送 AI 生成的流式内容、工具执行状态、会话更新通知等，WebSocket 是天然的选择。

2. **长连接**：HTTP 每次请求都需要建立连接、握手、关闭连接，开销大。WebSocket 建立一次连接后持续复用，减少了网络开销和延迟。

3. **心跳机制**：我们实现了 30 秒心跳检测，3 次未响应自动断开，配合 60 秒的事件缓冲区，客户端断线重连后可以自动重放丢失的事件，保证数据完整性。

**问：为什么误操作率能从 15% 降到 2%？**

答：我们设计了三级权限系统：

1. **safe 模式**（只读）：所有写操作被拦截，适合探索代码库阶段。

2. **ask 模式**（询问，默认）：写操作需要人工确认。我们维护了一个危险命令黑名单（rm、sudo、git push 等），这些命令强制弹窗确认。

3. **allow-all 模式**（自动）：适合自动化脚本，但需要用户主动切换（Shift+Tab）。

实际测试中，大部分误操作发生在用户"忘记当前在哪个会话"或"AI 理解错意图"的场景。默认的 ask 模式强制用户在执行前再次确认，就像代码审查一样，能拦截 87% 的误操作。

#### 1. JSONL 增量存储优化

**文件位置：** `packages/shared/src/sessions/jsonl.ts`

**为什么用 JSONL 而不是 JSON？**

| 特性 | JSON | JSONL |
|------|------|-------|
| 追加写入 | 需要重写整个文件 | 只追加一行 |
| 增量读取 | 必须全部加载 | 可以只读 header |
| 崩溃恢复 | 文件损坏则全丢 | 只丢失最后一行 |
| 内存占用 | O(n) | O(1) header 读取 |

**核心设计：**

1. **文件格式**
   ```
   session.jsonl:
   
   第 1 行：SessionHeader（元数据）
   {
     "id": "abc123",
     "name": "修复登录 bug",
     "messageCount": 42,           // 预计算
     "preview": "帮我看看登录接口...",  // 预计算
     "lastMessageRole": "assistant", // 预计算
     "tokenUsage": { ... },         // 预计算
     "createdAt": 1234567890
   }
   
   第 2 行：用户消息
   {"role":"user","content":"帮我看看登录接口为什么报 401"}
   
   第 3 行：助手消息
   {"role":"assistant","content":"让我看看代码..."}
   
   ... 以此类推
   ```

2. **Header Only 读取**
   ```typescript
   // 列表加载：只读第一行（8KB 缓冲区）
   function readSessionHeader(sessionFile: string): SessionHeader | null {
     const fd = openSync(sessionFile, 'r');
     const buffer = Buffer.alloc(8192);  // 只读 8KB
     const bytesRead = readSync(fd, buffer, 0, 8192, 0);
     closeSync(fd);
     
     const firstLine = buffer.toString('utf-8', 0, bytesRead).split('\n')[0];
     return JSON.parse(firstLine);
   }
   
   // 结果：100 个会话的列表加载从 2s → <100ms
   ```

3. **原子写入（Atomic Write）**
   ```typescript
   function writeSessionJsonl(sessionFile: string, session: StoredSession) {
     // 1. 写入临时文件
     const tmpFile = sessionFile + '.tmp';
     writeFileSync(tmpFile, jsonlContent);
     
     // 2. 原子重命名（覆盖原文件）
     renameSync(tmpFile, sessionFile);
     
     // 好处：进程崩溃只会损坏 .tmp，原文件完整
   }
   ```

4. **防抖持久化队列**
   ```typescript
   // packages/shared/src/sessions/persistence-queue.ts
   class SessionPersistenceQueue {
     private pending = new Map<string, PendingWrite>();
     private debounceMs = 500;  // 500ms 防抖
     
     enqueue(session: StoredSession): void {
       // 1. 取消之前的定时器
       const existing = this.pending.get(session.id);
       if (existing) clearTimeout(existing.timer);
       
       // 2. 新建定时器
       const timer = setTimeout(() => {
         this.write(session.id);
       }, this.debounceMs);
       
       // 3. 缓存最新数据
       this.pending.set(session.id, { data: session, timer });
     }
   }
   
   // 好处：AI 流式输出时，每秒 10+ 次更新合并为 2 次写入
   ```

#### 2. Jotai 原子化状态管理

**文件位置：** `apps/electron/src/renderer/atoms/sessions.ts`

**为什么选 Jotai 而不是 Redux？**

| 框架 | 优势 | 劣势 |
|------|------|------|
| Redux | 中心化状态，调试方便 | 模板代码多，性能差 |
| Jotai | 原子化，按需订阅 | 调试稍难 |

**核心设计：atomFamily**

```typescript
// 每个 Session 一个独立的 Atom
export const sessionAtomFamily = atomFamily(
  (sessionId: string) => atom<Session | null>(null),
  (a, b) => a === b  // 相同 sessionId 复用 atom
);

// 使用
const session1Atom = sessionAtomFamily('session-1');
const session2Atom = sessionAtomFamily('session-2');

// 更新 session1 时，只有订阅 session1Atom 的组件会重渲染
// session2 的组件完全不受影响
```

**解决的问题：**

```
旧方案（全局 Redux Store）：
┌────────────────────────────────────────────┐
│  Redux Store                               │
│  sessions: {                               │
│    'session-1': { messages: [...] },       │
│    'session-2': { messages: [...] }        │
│  }                                         │
└────────────────────────────────────────────┘
         │
         ├─────> ChatView(session-1) 重渲染 ✅
         │
         └─────> ChatView(session-2) 也重渲染 ❌
                 （即使数据没变）

新方案（Jotai atomFamily）：
┌─────────────┐  ┌─────────────┐
│ session-1   │  │ session-2   │
│    Atom     │  │    Atom     │
└─────────────┘  └─────────────┘
      │                 │
      │                 │
      ▼                 ▼
 ChatView(1)       ChatView(2)
 重渲染 ✅          不重渲染 ✅
```

**性能对比：**

| 场景 | Redux | Jotai | 改进 |
|------|-------|-------|------|
| 同时打开 3 个会话，其中 1 个 AI 流式输出 | 3 个视图全部重渲染 | 只有 1 个视图重渲染 | ↓ 66% |
| 列表滚动时更新未读标记 | 所有会话重渲染 | 只有被标记的会话重渲染 | ↓ 95% |

**问：JSONL 格式如何支持 1M+ tokens 的会话？**

#### 3. electron-builder 跨平台构建

**核心挑战：Native 依赖的平台差异**

这个项目依赖了多个 Native 二进制：

1. **Claude SDK (`@anthropic-ai/claude-agent-sdk`)**
   - 210 MB 的原生二进制
   - 每个平台都不同：`claude-darwin-arm64`、`claude-win32-x64` 等

2. **ripgrep (`@vscode/ripgrep`)**
   - Rust 编写的搜索工具
   - 每个平台都有预编译版本

3. **Bun Runtime**
   - 捆绑的 Bun 可执行文件
   - 用于运行子进程脚本

**解决方案：extraResources + 平台过滤**

```yaml
# electron-builder.yml

# macOS 构建
mac:
  extraResources:
    # 只包含 macOS 的二进制
    - from: node_modules/@anthropic-ai/claude-agent-sdk-binary
      to: app/node_modules/@anthropic-ai/claude-agent-sdk-binary
  files:
    # 排除其他平台
    - "!**/resources/bin/win32-*/**"
    - "!**/resources/bin/linux-*/**"

# Windows 构建
win:
  extraResources:
    # 只包含 Windows 的二进制
    - from: vendor/bun/bun.exe
      to: vendor/bun/bun.exe
    - from: resources/bin/win32-x64
      to: app/resources/bin/win32-x64
  files:
    # 排除其他平台
    - "!**/resources/bin/darwin-*/**"
    - "!**/resources/bin/linux-*/**"

# Linux 构建
linux:
  files:
    # 排除其他平台
    - "!**/resources/bin/darwin-*/**"
    - "!**/resources/bin/win32-*/**"
```

**构建脚本：**

```bash
# scripts/build-dmg.sh（macOS）
#!/bin/bash

# 1. 清理旧构建
rm -rf apps/electron/release

# 2. 安装目标平台的 SDK
cd apps/electron
ARCH=$(uname -m)
if [ "$ARCH" = "arm64" ]; then
  bun add @anthropic-ai/claude-agent-sdk-darwin-arm64 --optional
else
  bun add @anthropic-ai/claude-agent-sdk-darwin-x64 --optional
fi

# 3. 创建符号链接（统一路径）
ln -sf node_modules/@anthropic-ai/claude-agent-sdk-darwin-* \
       node_modules/@anthropic-ai/claude-agent-sdk-binary

# 4. 构建 Electron
bun run electron:build

# 5. 打包 DMG
electron-builder --config electron-builder.yml --mac

# 结果：Craft-Agents-arm64.dmg（或 x64.dmg）
```

#### 4. GitHub Actions 多平台并行构建

**文件位置：** `.github/workflows/build.yml`

**并行构建矩阵：**

```yaml
name: Build

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    strategy:
      matrix:
        include:
          # macOS（两个架构）
          - os: macos-14          # M1 Runner
            arch: arm64
            script: build-dmg.sh
          - os: macos-13          # Intel Runner
            arch: x64
            script: build-dmg.sh
          
          # Windows
          - os: windows-latest
            arch: x64
            script: build-win.ps1
          
          # Linux
          - os: ubuntu-latest
            arch: x64
            script: build-linux.sh
    
    runs-on: ${{ matrix.os }}
    
    steps:
      - uses: actions/checkout@v4
      
      # 安装 Bun
      - uses: oven-sh/setup-bun@v2
        with:
          bun-version: latest
      
      # 安装依赖
      - run: bun install
      
      # 构建
      - run: bash scripts/${{ matrix.script }}
        if: runner.os != 'Windows'
      - run: powershell scripts/${{ matrix.script }}
        if: runner.os == 'Windows'
      
      # 上传构建产物
      - uses: actions/upload-artifact@v4
        with:
          name: Craft-Agents-${{ matrix.os }}-${{ matrix.arch }}
          path: apps/electron/release/*
```

| 并行构建（4 个 Runner） | **35 分钟** | 4 个平台同时构建，取最慢的 |

#### 5. 平台差异处理实例

**问题 1：Windows 文件路径**

```typescript
// ❌ 错误：Unix 路径在 Windows 失效
const path = '/Users/john/workspace';

// ✅ 正确：使用 Node.js path 模块
import { join, normalize } from 'path';
const path = join(homedir(), 'workspace');  // 自动适配 Windows
```

**问题 2：Windows EBUSY 文件锁**

```yaml
# electron-builder.yml

# ❌ 问题：Windows 打包时 bun.exe 被占用
files:
  - vendor/bun/bun.exe  # electron-builder 扫描时会锁定 .exe 文件

# ✅ 解决：使用 extraResources 提前复制
extraResources:
  - from: vendor/bun/bun.exe
    to: vendor/bun/bun.exe
```

**问题 3：macOS 代码签名**

```yaml
# electron-builder.yml
mac:
  hardenedRuntime: true
  gatekeeperAssess: false
  entitlements: build/entitlements.mac.plist
  
  # 需要的权限
  # - com.apple.security.cs.allow-unsigned-executable-memory
  # - com.apple.security.network.client
  # - com.apple.security.network.server
```

**问题 4：Linux AppImage 权限**

```bash
# build-linux.sh

# 给所有 .sh 脚本添加执行权限
chmod +x resources/bin/*.sh
chmod +x resources/bridge-mcp-server/run.sh

# 打包后的 AppImage 自动包含这些权限
```

### 可展开的面试话术

**问：为什么选择 Bun 而不是 npm？**

答：主要是性能和开发体验：

1. **安装速度**：Bun 比 npm 快 10 倍，全新安装从 120 秒降到 12 秒。
2. **原生 TypeScript**：不需要 ts-node 或 tsx，直接 `bun run script.ts`。
3. **内置工具链**：测试、打包、任务运行器都内置，减少了工具链复杂度。
4. **Monorepo 支持**：Workspaces 性能比 npm 好，依赖安装和链接都更快。

**问：跨平台构建有哪些坑？**

答：主要是 Native 依赖的平台差异：

1. **Claude SDK**：210 MB 的原生二进制，每个平台都不同。我们用 electron-builder 的 `extraResources` 机制，在构建时只包含目标平台的二进制，避免打包体积膨胀。

2. **Windows 文件锁**：electron-builder 扫描 node_modules 时会锁定 .exe 文件，导致复制失败。解决方案是把这些文件移到 `extraResources`，在扫描前就复制完成。

3. **macOS 代码签名**：需要配置 Hardened Runtime 和 Entitlements，否则 Gatekeeper 会阻止运行。我们用了 `com.apple.security.cs.allow-unsigned-executable-memory` 权限来运行子进程。

4. **并行构建**：用 GitHub Actions 的 matrix 策略，4 个平台同时构建，总时间从 120 分钟降到 35 分钟。

**问：Monorepo 的好处是什么？**

答：统一管理和代码复用：

1. **共享代码**：所有业务逻辑在 `packages/shared`，Electron、Server、CLI 三个前端都能用，避免重复实现。

2. **统一版本**：一个 package.json 管理所有依赖版本，避免 Electron 用 React 18、WebUI 用 React 17 的情况。

3. **快速迭代**：修改 `packages/shared` 后，所有应用立即生效，不需要发布 npm 包、更新版本号。

4. **类型共享**：TypeScript 类型在所有 packages 间共享，前后端接口自动同步。
